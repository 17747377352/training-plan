## 数据同步现状

### 触发方式

| 方式 | 回溯天数 | 说明 |
|---|---|---|
| 首次绑定弹窗 | 15 天 | 绑定成功后询问，选择「暂不」不影响后续 |
| 每日定时 | **3 天** | 每天 09:00；回溯 3 天以覆盖前一晚骑行与数据延迟修正，在飞任务自动跳过 |
| 手动同步 | 7 天 | 账号列表的「同步」按钮；接口可自定义 `days` |

### 同步内容

| 数据类型 | 表 | 关键字段 |
|---|---|---|
| 每日健康 | `daily_health` | 步数、距离、静息心率、心率区间、压力、身体电量 |
| 睡眠 | `sleep_record` | 总时长、深/浅/REM/清醒、睡眠评分、睡眠 HRV、血氧、呼吸 |
| HRV | `hrv_record` | 夜间值、7 日均值、状态、个人基线区间 |
| 骑行活动 | `activity` | 距离、爬升、移动时间、AP/NP/TSS/IF、左右平衡、Z1–Z7、踏频 |

### 实测数据

- 3 天同步耗时 5 秒；30 天约 40 秒；90 天约 90 秒（逐日拉取，共 270 次请求）。
- HRV 与骑行距离均与用户手工导出的 Garmin CSV **完全一致**，交叉验证通过。

## Garmin 登录突破（2026-09-20）

程序登录此前被 Garmin 的 SSO 防护完全挡住（5 段策略全失败：4 段 429、1 段 403 人机挑战）。关键结论：

- **瓶颈在 SSO，不在数据接口。** 拿到令牌后恢复会话只需 1 秒，API 层从未被限流。
- **`curl_cffi` 只伪装 TLS 指纹，不执行 JS**，过不了 Cloudflare 挑战；把库内部的 `requests.Session` 替换为 `cloudscraper` 会话后，8 秒完成登录。做法来自 `freakyflow/garminskill`，但原写法针对 0.2.x，0.3.16 需改为替换 `requests.Session` 类本身。
- **可重复性依赖 Garmin 当时的限流状态。** 同一天内同一个补丁先成功后失败一次（Garmin 从 403 升级为 `CAPTCHA required`）。因此令牌导入是主路径，凭证登录是备用。

## 已知设计约束

- **Garmin 登录耗时长，超时必须逐层放大。** 官方库会依次尝试多段登录策略，实测国际站一次失败登录约 30 秒。因此超时层级必须是「前端 150 秒 > 后端调采集器 120 秒 > 采集器等 Garmin」，任何一层小于实际耗时都会把"Garmin 慢"误报成别的故障。
- **Garmin 会对登录端点限流。** `sso.garmin.com` 在频繁尝试后返回 429 或 HTML 挑战，库的登录链会逐个策略重试到超时。采集器已区分 `RATE_LIMITED` 与 `UNREACHABLE`，并且**一旦出现就进入冷却期**（默认 900 秒），冷却期内不再触碰 Garmin。排查时不要反复重试。
- **浏览器能登录不代表程序能登录。** 浏览器能通过 Cloudflare 人机挑战并使用既有会话，而程序登录必须走未认证的 SSO 端点。
- **云爬虫绕过会周期性失效。** `cloudscraper` 只能处理经典 IUAM JS 挑战；Garmin 若改用 CAPTCHA 或托管挑战则失效（已实测遇到一次）。可用 `COLLECTOR_DISABLE_CLOUDFLARE_BYPASS=1` 关闭以定位问题。
- **MFA 会话不能放进 Redis。** `resume_login(client_state, mfa_code)` 需要存活的客户端对象，`client_state` 不可序列化。会话保存在 Collector 进程内存（TTL 600 秒、上限 100 个）。**Collector 首期必须单副本部署**，否则提交验证码的请求可能落到没有该会话的副本。
- **冷却期只保护 SSO 端点。** 令牌恢复路径只访问 API 层（实测 1 秒），不受 SSO 限流连坐。
- **时间字段格式。** Garmin 用空格分隔（`2026-09-19 08:53:51`），平台统一按 ISO 存储；采集器负责转换，后端解析容忍两种写法。
- **实体字段与列名的映射规则。** MyBatis-Plus 仅在大写字母前插下划线，**数字前后不插**：`max20minPower` → `max20min_power`。含数字的字段需加 `@TableField` 显式映射，`EntitySchemaConsistencyTest` 会拦住错配。
- **Token 加密密钥必须备份。** `app.security.token-cipher-key` 丢失后已存储的 Garmin Token 无法解密，所有账号都需要重新认证。
- **禁用用户的即时性。** access token 是无状态的，禁用后最长 15 分钟内仍能通过签名校验；但 `login`、`refresh` 和 `UserService.getProfile` 都会检查状态。新增业务接口时需沿用"读取用户状态"的做法。
- **首个管理员需人工提升。** 注册只分配 `USER` 角色，需在数据库中手动授予 `ADMIN`。
- **健康数据查询区间上限 366 天。** 区间超限或起止倒置都返回 `40000`，避免一次请求把整表拉出来；趋势看板只查 7 / 30 / 90 天（并向后再取一个等长周期用于环比）。
- **不要照抄 `garminconnect` typed 模型的睡眠字段名。** 现象：`sleep_record.avg_sleep_hrv` 与 `avg_spo2` 连续 20 天全为 `NULL`。原因：采集器按库的 `SleepData` 用 `avgSleepHRV`/`avgSpO2` 取值，而这两个别名只存在于库的 `tests/test_typed.py` **手写 fixture**（`userProfilePK: 12345`）里，真实响应从来没有这两个键——真实键名是 `dailySleepDTO.averageSpO2Value` 和**顶层**的 `avgOvernightHrv`（不在 `dailySleepDTO` 里）。规避：字段名一律以实拉响应为准（`_activity_row` 当初就是这么做的），已修正映射并补测试；补齐历史数据只需再跑一次 20 天同步。另注：`averageSpO2HRSleep` 是「睡眠期间的平均心率」而非血氧；`avgOvernightHrv` 与 `hrv_record.last_night_avg` 实测逐日完全一致，可互为交叉校验。
- **恢复标记的阈值目前是固定常量。** 静息心率高于个人 7 日基线 5 bpm 记「需留意」、10 bpm 记「需重视」，睡眠不足 6 小时记「需留意」，连续 3 天未恢复升级为「需重视」，基线至少要有 3 天样本。阈值集中在 `TrendsView.vue` 顶部常量里，先用真实数据观察一段时间再决定是否放宽或改成可配置。
- **断言越权与状态流转时不能只看整条 SQL。** MyBatis-Plus 的 `Wrapper` 里 `set()` 和 `in()` 的参数混在同一个 `paramNameValuePairs`，条件被放宽也照样能通过断言；必须只按 `getSqlSegment()`（WHERE 片段）里的占位符取值，且 `getParamNameValuePairs()` 要先调 `getSqlSet()`/`getSqlSegment()` 才有内容。同理，只断言「参数里有当前用户 ID」挡不住 `eq(user_id, ?)` 被误写成 `eq(id, ?)`（参数值完全相同），要同时断言列名。以上都做了变异测试确认能捕获对应误改。
- **任务状态流转必须带状态条件，否则迟到的队列消息会改写终态。** 现象：一条任务被清理器判超时后，队列里那条还没被消费的消息会在采集器恢复后被处理，把已失败的任务重新推成 `RUNNING`/`SUCCESS`（实测任务 #16 就这样从 `FAILED` 变成 `SUCCESS`，还留着旧的失败原因，看板上成了「成功 + Garmin接口请求过于频繁」）。原因：`markRunning`/`complete`/`fail` 原先都按主键无条件更新。规避：三处改为带状态条件的更新——开跑只接受 `PENDING → RUNNING`（不满足则拒绝，本次执行作废）、完成只接受 `PENDING`/`RUNNING`、失败上报不覆盖已成功的任务；完成时显式 `set(error_code/error_message, null)`（`updateById` 会忽略 null 字段）。`V6` 迁移已修复历史数据。
- **平台内部接口用 HTTP 200 + 业务码表示失败，采集器必须看 `code`。** 只看 `raise_for_status()` 会把「任务已作废」当成执行成功，采集器继续拉数、继续回传，日志还打出 `sync_job_succeeded`。`_post` 现在校验响应体里的 `code`，非 200 抛 `CollectorApiError` 并立刻停手。
- **多列合并的 `ALTER TABLE` 会被静态一致性测试漏掉。** `EntitySchemaConsistencyTest` 原先用 `ALTER TABLE (\w+)\s+ADD COLUMN (\w+)` 匹配，一条 ALTER 里并列多个 `ADD COLUMN` 时只认第一个，后面几列改名也不会报错。已改为先按分号切出 ALTER 语句本体、再逐个匹配 `ADD COLUMN`，并先去掉行注释。
- **`get_sleep_daily` 不是富睡眠接口，不能拿来「优化」逐日循环。** 它请求的是 `/sleep-service/stats/sleep/daily`，返回 `{calendarDate, values}` 指标序列，**没有 `dailySleepDTO`**，用它替换会静默丢掉睡眠分期、评分、血氧与睡眠 HRV。压力与最大/最小心率同样没有区间接口。所以 200 天补数据的请求数是 381（睡眠与每日统计仍逐日）而不是 10——只有 HRV 能走 `get_hrv_data_range` 一次取整段。
- **FTP 历史接口的区间上限约一年，超了会被 400 拒绝。** 现象：用 `"2000-01-01"` 请求时 FTP 只落 1 条，看起来像正常结果。原因：Garmin 返回 `End date is before start date or maximum range`，而 `_safe` 把异常吞掉，于是静默退化成「只有当前值一条」。规避：显式限定一年窗口，并有用例断言区间跨度不超过 366 天。
- **Garmin 的 typed 模型不能当字段字典用，必须实拉核对。** 已踩两次：`SleepData` 的 `avgSleepHRV`/`avgSpO2` 只存在于库的手写 fixture（见上一条），`get_functional_threshold_power_range` 的 `sport` 默认值是 `"RUNNING"`（取骑行 FTP 必须显式传 `"CYCLING"`）。
- **打卡接口是替换语义而不是合并。** `PUT /api/checkins/{date}` 未传的字段会被置空，例如先填了备注、之后只传体重会把备注清掉（前端表单始终带上备注所以无感）。字段级合并需要改成 PATCH 语义。
- **训练状态的负荷平衡是 4 周滚动窗口。** `monthlyLoad*` 是 Garmin 按最近四周累计出的结果，所以「诊断」会滞后于最近的单次训练；判断当天的加减量应以 ACWR 与 HRV/静息心率为主，负荷平衡用来看长期结构。
- **判灯门槛与处方的松紧必须配套，否则绿灯会变成死代码。** 现象：`readiness-v1` 要求四项恢复依据齐全才给绿灯，而四个维度里只有 RPE 需要人工填写，实测本地 200 天**绿灯 0 天**（黄灯 139、红灯 61），`可用依据` 为 3/4 的有 184 天。原因：缺一项就压灯，而「一项不缺」几乎不可能成立。更糟的是它与训练目标冲突——同期 Garmin 诊断为 `AEROBIC_LOW_SHORTAGE`（低强度有氧只有目标下限 36%），引擎却因缺一条手填数据把每天都锁在 20 分钟 Z1 恢复骑上，恰恰不给最该练的 Z2。规避：`readiness-v2` 把门槛降到 3 项，**同时**把缺证据时的处方收紧（45 分钟且标注「已收紧」，四项齐全才给 60 分钟）——只降门槛不收紧上限等于单方面放松安全规则。改后实测绿灯 0 → **57 天**，全部拿到 45 分钟 Z2。AI 那条路的上限同步收紧（缺一项 45 分钟/70%）。
- **`acwrStatus` 与 `acwrRatio` 实测完全一致，比值判断只是兜底。**- **`acwrStatus` 与 `acwrRatio` 实测完全一致，比值判断只是兜底。** 200 天数据里无一处重叠：`LOW` 0.00–0.70、`OPTIMAL` 0.80–1.40、`HIGH` 1.50–1.90、`VERY_HIGH` 2.00–2.80。所以引擎里那两条比值判断（1.5 / 2.0）在正常数据下与状态判断等价，只在状态字段为空时才起作用。
- **AI 生成结果必须落库，否则刷新即失。** 现象：生成后刷新页面计划就不见了。原因：接口只返回 DTO、不落库，前端放在 `ref` 里。规避：`training_plan` 表 + `GET /api/training-plans` 读回；`GET` 未生成过时 `data` 字段会被 NON_NULL 序列化整个省略，前端统一成 `null` 处理。
- **训练目标不能放宽安全上限，这是刻意设计。** 目标只写进 AI 上下文影响「练什么」，不参与判灯，也无法改动 `constraints` 的 `maxDurationMinutes`/`maxFtpPercent`/`noIntervals`。若让目标能放宽上限，用户把目标写成「提升功率」即可绕过恢复判灯，安全规则会变成空话。**目标是需求，不是许可。** 要在绿灯下做真正的阈值/间歇课，需要单独决定是否提高绿灯的强度上限（当前 75%），不应由目标字段自动触发。
- **午睡原先整块丢弃，现在只记录不判灯。** 现象：日志里 `sleep=7`（7 天 7 条）看起来正常，但 2026-09-21 用户明确午睡了 43 分钟，库里只有夜间 5.3 小时。原因：采集器 `_sleep_row` 只读 `dailySleepDTO` 的主睡眠字段，`napTimeSeconds` 与 `dailyNapDTOS` 两个字段都没有映射——**「行数对得上」不等于「数据没丢」**，因为主睡眠本来就只有一行。规避：`nap_record` 按次存储（`dailyNapDTOS` 是数组，一天可多条；单列合计会丢掉第二次），要求有 `napStartTimestampGMT` 才入库以便幂等去重。**是否计入判灯留待单独决定**，理由与具体影响见 `docs/训练建议规则.md` 第五节。
- **注册开关默认必须是关闭，而且这个「默认」需要测试守着。** 开放注册意味着任何人注册后即可调用付费的 AI 接口。默认值写在两处：`AuthServiceImpl` 的 `@Value("${app.security.registration-enabled:false}")` 与随包发布的 `application.yml`。单测用反射显式设置开关，**绕过了默认值**，所以把默认改成 `true` 不会让任何用例失败（变异测试发现的缺口）；`RegistrationSwitchTest` 因此做静态检查，既看注解默认值也看 `application.yml`，改任一处都会失败。生产要开放时用环境变量 `REGISTRATION_ENABLED=true`，不要改默认值。
- **用量日志必须写在独立事务里，读也一样。** 现象：接口返回 `AI_INVALID_RESPONSE`，而 `ai_generation_log` 一行都没有，配额显示 0。原因：`generate` 带 `@Transactional`，失败时抛异常回滚，把同一事务里的用量 insert 一起回滚了——**配额少算、花费少报**。读取同理：MySQL 默认 REPEATABLE READ，外层事务的快照看不到刚提交的记录，于是「生成成功」的响应里显示「已用 0 次」。规避：`recordSuccess`/`recordFailure`/`recordReuse`/`usage` 全部 `REQUIRES_NEW`；这个性质单测观察不到，用反射测试钉住，防止被顺手删掉。
- **AI 花费是真金白银，配额与用量必须可审计。** 实测一次生成约 1.3 万输入 + 约 500 输出 token、耗时 3.7–4.1 秒。指纹复用能省掉重复调用：同一份数据第二次生成 `reused=true`，零成本。这两条是上线前的前置条件——在此之前，只要注册开放，任何人都能无限次调用付费接口。
- **删除账号暂不级联删除同步数据。** `sync_job` 与各数据表对 `garmin_account` 有外键约束，需要在同一事务里先清理。
- **profile 配置里写死的字面量会静默吃掉环境变量，生产配置必须保留占位符。** 现象：生产点「绑定 Garmin」总是报「Garmin 采集服务暂不可用」（46005），而后端错误日志里打印的 `target=http://127.0.0.1:8090` 与实际监听的 18090 不符；采集器本身是好的——`/health` 在 18090 返回 200，用同一个 token 请求 `/internal/garmin/verify-token` 返回 **422**（字段缺失）而不是 401，证明地址与凭据都有效。原因：`app.collector.base-url` 在 `application.yml` 里是 `${COLLECTOR_BASE_URL:http://127.0.0.1:8090}`，而 `application-prod.yml` 又把它**写死**成 8090；Spring Boot 的 profile 配置优先级高于基础配置，占位符的解析结果被整个覆盖，compose 里注入的 `COLLECTOR_BASE_URL: http://127.0.0.1:18090` 因此被静默忽略（实测 `docker exec training-plan-server env` 里该变量确实是 18090，应用却用 8090）。注意这与 `SPRING_DATASOURCE_*` 不同：那类变量直接绑定同名属性、优先级高于 yml，所以出问题的只会是 `app.*`。规避：`application-prod.yml` 里凡 `application.yml` 用 `${ENV:默认值}` 声明的属性一律保留占位符，默认值填本机原值以保证本地跑 prod profile 行为不变，采集器地址的默认值同时改为 18090；新增 `ProdConfigOverrideTest` 静态比对两份文件，重新写死会让它失败（该用例先在未修复的文件上确认过能报出全部 7 处覆盖）。
- **Garmin 登录端点按 IP 限流，配额小到「一次成功之后立刻 429」——这是整个绑定方案的约束来源。** 实测：本机（住宅 IP）用 `garminconnect` 0.3.16 + cloudscraper 跑生产同款策略集，`mobile+requests` 第一次就登录成功且不需要 MFA；紧接着再请求同一个端点（`POST sso.garmin.com/sso/mobile/api/login`）就返回 **HTTP 429**，正文是 Garmin 自己的 `{"error":{"status-code":"429",...}}`。所以：
  - 用户「在页面上填账号密码」在服务器上**不可能**成立——所有用户共用一个出口 IP，第一个人成功、第二个人就被限流；
  - 生产服务器上五段策略的实际结果：`mobile+cffi` 429、`mobile+requests` 429、`widget+cffi`「unexpected title *Update Phone Number*」（**它是唯一穿过 Cloudflare 的**，说明网页流程本身通，卡在人机验证）、`portal+cffi`「CAPTCHA required」×2 后 429、`portal+requests` HTTP 403；
  - 而**令牌**那条路完全不碰登录端点（只走 `diauth` 令牌交换与 `connectapi` 取数），服务器上实测正常——生产已用导入的令牌同步回 15 天数据；
  - 结论：登录必须发生在**用户自己的机器**上（各自一份 IP 配额），这也是桌面助手方案（本机登录 + 配对码回传令牌）的设计依据。库已是最新版 0.3.16，升级无解；`client.py` 里连 `Retry-After` 都没有处理。
  - 排查提示：`login()` 的循环把每段失败打成 WARNING，但措辞是「xxx returned 429」，按关键词过滤日志时极易漏掉——本次就先误判成「mobile 静默失败」。
- **静态文件权限不对，表现是线上 403 而部署全程无报错。** 现象：部署成功、容器健康、页面正常，但下载 `https://songtop.xyz/plan/garmin_pair_helper.py` 返回 403（162 字节的 nginx 错误页）。原因：该文件在本地创建时权限是 `600`（受 umask 影响），tar 打包原样保留，而 nginx 以别的用户运行读不到。同一个目录里其它文件是 644，所以只有这一个文件出问题，极易漏掉。规避：部署脚本在打包后统一 `chmod -R a+rX "$bundle/web"`（`a+rX` 只给目录补执行位，不会把普通文件变成可执行），并加一条断言「bundle 里不允许有 others 不可读的文件」——宁可在部署阶段失败，也不要上线后让用户撞 403。注意：验证时要看**真正被服务的那条路径**，`/var/www/plan` 是 web-release 的软链，`/opt/training-plan/current/web` 只是打包在 server 发布里的副本，两者不是同一个文件；另外 `remote-deploy*.sh` 是**有意**设成 750 的，不要被无差别的 chmod 放开。
- **`docker cp` 写进 tmpfs 挂载点会静默失效。** 现象：`docker cp script.py training-plan-collector:/tmp/script.py` 退出码为 0，但容器里 `ls /tmp` 为空、`python /tmp/script.py` 报文件不存在。原因：采集器 compose 里 `/tmp` 是 `tmpfs` 挂载，`docker cp` 实际写到了挂载点下面的 overlay 目录，被 tmpfs 遮住。规避：往非 tmpfs 路径拷（如 `/opt/app/`），或改用 `docker exec -i ... python -` 从标准输入喂脚本。
- **判断「表里有没有数据」不能用 `information_schema.TABLE_ROWS`。** 现象：生产库这台机器上它报 `daily_health=201`、`activity=50`、`garmin_account=1`、`sys_user=4`，看起来生产已经有数据（文档「已入库数据」那一行就是这么读出来的）；实际 `SELECT COUNT(*)` 全是 **0**（只有 1 个账号）。原因：`TABLE_ROWS` 是存储引擎的估算值，且受 `information_schema_stats_expiry` 缓存影响，默认可陈旧 24 小时——它反映的是这批表**曾经**的行数。规避：涉及数据有无、是否丢数据的判断一律用精确 `COUNT(*)`；本文件里的数据量只写实测值并注明库别（本地开发库 / 生产库）。
- **比对环境变量与配置文件里的密钥时，哈希要在同一种算法下算。** 现象：用 `printenv VAR | sha256sum` 与本地 `printf '%s' "$V" | shasum -a 256` 比对，四个密钥的指纹**全都不一样**，看起来像生产注入值早已与配置脱节；实际两边完全相同。原因：那次比对把命令塞进了多层 `ssh '...' + docker exec sh -c "..."` 的嵌套引号里，内层 `printenv` 取到的值与预期不符（本地那次也没带上 `printenv` 输出自带的换行）。规避：改用 `ssh host bash -s <<'REMOTE'` 的 heredoc 形式消除引号歧义，并让两边都按「值 + 换行」计算；更重要的是，拿一组**已知相等**的值做交叉验证——本次正是靠 `COLLECTOR_SERVER_TOKEN` 与 `COLLECTOR_SERVICE_TOKEN` 实测同值，才发现是方法错了而不是环境错了。
