## Garmin 登录突破（2026-09-20）

程序登录此前被 Garmin 的 SSO 防护完全挡住（5 段策略全失败：4 段 429、1 段 403 人机挑战）。关键结论：

- **瓶颈在 SSO，不在数据接口。** 拿到令牌后恢复会话只需 1 秒，API 层从未被限流。
- **`curl_cffi` 只伪装 TLS 指纹，不执行 JS**，过不了 Cloudflare 挑战；把库内部的 `requests.Session` 替换为 `cloudscraper` 会话后，8 秒完成登录。做法来自 `freakyflow/garminskill`，但原写法针对 0.2.x，0.3.16 需改为替换 `requests.Session` 类本身。
- **可重复性依赖 Garmin 当时的限流状态。** 同一天内同一个补丁先成功后失败一次（Garmin 从 403 升级为 `CAPTCHA required`）。因此令牌导入是主路径，凭证登录是备用。

## 已知设计约束

- **Garmin 登录耗时长，超时必须逐层放大。** 官方库会依次尝试多段登录策略，实测国际站一次失败登录约 30 秒。因此超时层级必须是「前端 150 秒 > 后端调采集器 120 秒 > 采集器等 Garmin」，任何一层小于实际耗时都会把"Garmin 慢"误报成别的故障。
- **Garmin 会对登录端点限流。** `sso.garmin.com` 在频繁尝试后返回 429 或 HTML 挑战，库的登录链会逐个策略重试到超时。采集器已区分 `RATE_LIMITED` 与 `UNREACHABLE`，并且**一旦出现就进入冷却期**（默认 900 秒），冷却期内不再触碰 Garmin。排查时不要反复重试。
- **浏览器能登录不代表程序能登录。** 浏览器能通过 Cloudflare 人机挑战并使用既有会话，而程序登录必须走未认证的 SSO 端点。
- **云爬虫绕过会周期性失效。** `cloudscraper` 只能处理经典 IUAM JS 挑战；Garmin 若改用 CAPTCHA 或托管挑战则失效（已实测遇到一次）。可用 `COLLECTOR_DISABLE_CLOUDFLARE_BYPASS=1` 关闭以定位问题。
- **MFA 会话不能放进 Redis。** `resume_login(client_state, mfa_code)` 需要存活的客户端对象，`client_state` 不可序列化。会话保存在 Collector 进程内存（TTL 600 秒、上限 100 个）。**Collector 首期必须单副本部署**，否则提交验证码的请求可能落到没有该会话的副本。
- **冷却期只保护 SSO 端点。** 令牌恢复路径只访问 API 层（实测 1 秒），不受 SSO 限流连坐。
- **时间字段格式。** Garmin 用空格分隔（`2026-09-19 08:53:51`），平台统一按 ISO 存储；采集器负责转换，后端解析容忍两种写法。
- **实体字段与列名的映射规则。** MyBatis-Plus 仅在大写字母前插下划线，**数字前后不插**：`max20minPower` → `max20min_power`。含数字的字段需加 `@TableField` 显式映射，`EntitySchemaConsistencyTest` 会拦住错配。
- **Token 加密密钥必须备份。** `app.security.token-cipher-key` 丢失后已存储的 Garmin Token 无法解密，所有账号都需要重新认证。
- **禁用用户的即时性。** access token 是无状态的，禁用后最长 15 分钟内仍能通过签名校验；但 `login`、`refresh` 和 `UserService.getProfile` 都会检查状态。新增业务接口时需沿用"读取用户状态"的做法。
- **首个管理员需人工提升。** 注册只分配 `USER` 角色，需在数据库中手动授予 `ADMIN`。
- **健康数据查询区间上限 366 天。** 区间超限或起止倒置都返回 `40000`，避免一次请求把整表拉出来；趋势看板只查 7 / 30 / 90 天（并向后再取一个等长周期用于环比）。
- **不要照抄 `garminconnect` typed 模型的睡眠字段名。** 现象：`sleep_record.avg_sleep_hrv` 与 `avg_spo2` 连续 20 天全为 `NULL`。原因：采集器按库的 `SleepData` 用 `avgSleepHRV`/`avgSpO2` 取值，而这两个别名只存在于库的 `tests/test_typed.py` **手写 fixture**（`userProfilePK: 12345`）里，真实响应从来没有这两个键——真实键名是 `dailySleepDTO.averageSpO2Value` 和**顶层**的 `avgOvernightHrv`（不在 `dailySleepDTO` 里）。规避：字段名一律以实拉响应为准（`_activity_row` 当初就是这么做的），已修正映射并补测试；补齐历史数据只需再跑一次 20 天同步。另注：`averageSpO2HRSleep` 是「睡眠期间的平均心率」而非血氧；`avgOvernightHrv` 与 `hrv_record.last_night_avg` 实测逐日完全一致，可互为交叉校验。
- **恢复标记的阈值目前是固定常量。** 静息心率高于个人 7 日基线 5 bpm 记「需留意」、10 bpm 记「需重视」，睡眠不足 6 小时记「需留意」，连续 3 天未恢复升级为「需重视」，基线至少要有 3 天样本。阈值集中在 `TrendsView.vue` 顶部常量里，先用真实数据观察一段时间再决定是否放宽或改成可配置。
- **断言越权与状态流转时不能只看整条 SQL。** MyBatis-Plus 的 `Wrapper` 里 `set()` 和 `in()` 的参数混在同一个 `paramNameValuePairs`，条件被放宽也照样能通过断言；必须只按 `getSqlSegment()`（WHERE 片段）里的占位符取值，且 `getParamNameValuePairs()` 要先调 `getSqlSet()`/`getSqlSegment()` 才有内容。同理，只断言「参数里有当前用户 ID」挡不住 `eq(user_id, ?)` 被误写成 `eq(id, ?)`（参数值完全相同），要同时断言列名。以上都做了变异测试确认能捕获对应误改。
- **任务状态流转必须带状态条件，否则迟到的队列消息会改写终态。** 现象：一条任务被清理器判超时后，队列里那条还没被消费的消息会在采集器恢复后被处理，把已失败的任务重新推成 `RUNNING`/`SUCCESS`（实测任务 #16 就这样从 `FAILED` 变成 `SUCCESS`，还留着旧的失败原因，看板上成了「成功 + Garmin接口请求过于频繁」）。原因：`markRunning`/`complete`/`fail` 原先都按主键无条件更新。规避：三处改为带状态条件的更新——开跑只接受 `PENDING → RUNNING`（不满足则拒绝，本次执行作废）、完成只接受 `PENDING`/`RUNNING`、失败上报不覆盖已成功的任务；完成时显式 `set(error_code/error_message, null)`（`updateById` 会忽略 null 字段）。`V6` 迁移已修复历史数据。
- **平台内部接口用 HTTP 200 + 业务码表示失败，采集器必须看 `code`。** 只看 `raise_for_status()` 会把「任务已作废」当成执行成功，采集器继续拉数、继续回传，日志还打出 `sync_job_succeeded`。`_post` 现在校验响应体里的 `code`，非 200 抛 `CollectorApiError` 并立刻停手。
- **多列合并的 `ALTER TABLE` 会被静态一致性测试漏掉。** `EntitySchemaConsistencyTest` 原先用 `ALTER TABLE (\w+)\s+ADD COLUMN (\w+)` 匹配，一条 ALTER 里并列多个 `ADD COLUMN` 时只认第一个，后面几列改名也不会报错。已改为先按分号切出 ALTER 语句本体、再逐个匹配 `ADD COLUMN`，并先去掉行注释。
- **`get_sleep_daily` 不是富睡眠接口，不能拿来「优化」逐日循环。** 它请求的是 `/sleep-service/stats/sleep/daily`，返回 `{calendarDate, values}` 指标序列，**没有 `dailySleepDTO`**，用它替换会静默丢掉睡眠分期、评分、血氧与睡眠 HRV。压力与最大/最小心率同样没有区间接口。所以 200 天补数据的请求数是 381（睡眠与每日统计仍逐日）而不是 10——只有 HRV 能走 `get_hrv_data_range` 一次取整段。
- **FTP 历史接口的区间上限约一年，超了会被 400 拒绝。** 现象：用 `"2000-01-01"` 请求时 FTP 只落 1 条，看起来像正常结果。原因：Garmin 返回 `End date is before start date or maximum range`，而 `_safe` 把异常吞掉，于是静默退化成「只有当前值一条」。规避：显式限定一年窗口，并有用例断言区间跨度不超过 366 天。
- **Garmin 的 typed 模型不能当字段字典用，必须实拉核对。** 已踩两次：`SleepData` 的 `avgSleepHRV`/`avgSpO2` 只存在于库的手写 fixture（见上一条），`get_functional_threshold_power_range` 的 `sport` 默认值是 `"RUNNING"`（取骑行 FTP 必须显式传 `"CYCLING"`）。
- **打卡接口是替换语义而不是合并。** `PUT /api/checkins/{date}` 未传的字段会被置空，例如先填了备注、之后只传体重会把备注清掉（前端表单始终带上备注所以无感）。字段级合并需要改成 PATCH 语义。
- **训练状态的负荷平衡是 4 周滚动窗口。** `monthlyLoad*` 是 Garmin 按最近四周累计出的结果，所以「诊断」会滞后于最近的单次训练；判断当天的加减量应以 ACWR 与 HRV/静息心率为主，负荷平衡用来看长期结构。
- **判灯规则里 `可用依据 < 4 → 黄灯` 会让绿灯在实际使用中不可达。** 四个恢复维度中只有 RPE 需要人工填写，实测本地 200 天数据：绿灯 **0 天**、黄灯 139 天、红灯 61 天；`可用依据` 为 3/4 的有 184 天（差的都是 RPE）。**57 天（28.5%）仅因缺 RPE 无法变绿**——例：2026-07-12 三项 Garmin 指标全绿（有效训练 ACWR 0.90、HRV 77/85 在基线 69–92 内、睡眠 7.8 小时 86 分），未填 RPE 时是黄灯 + 20 分钟 Z1 恢复骑，补一条 `RPE=3` 立刻变绿灯 + 45 分钟 Z2 有氧。这与 Garmin 的 `AEROBIC_LOW_SHORTAGE`（低强度有氧只有目标下限 36%）直接冲突：引擎因缺一条手填数据，把每天都锁在恢复骑上，恰恰不给最该练的 Z2。**AI 那条路也绕不过去**，因为模型的上限同样由灯色给出（红灯 0 分钟/0%、黄灯 20 分钟/50%、绿灯 90 分钟/75%）。这是**尚未修改的产品取舍**，可选方向见 `docs/训练建议规则.md` 第三节。
- **`acwrStatus` 与 `acwrRatio` 实测完全一致，比值判断只是兜底。** 200 天数据里无一处重叠：`LOW` 0.00–0.70、`OPTIMAL` 0.80–1.40、`HIGH` 1.50–1.90、`VERY_HIGH` 2.00–2.80。所以引擎里那两条比值判断（1.5 / 2.0）在正常数据下与状态判断等价，只在状态字段为空时才起作用。
- **AI 生成结果必须落库，否则刷新即失。** 现象：生成后刷新页面计划就不见了。原因：接口只返回 DTO、不落库，前端放在 `ref` 里。规避：`training_plan` 表 + `GET /api/training-plans` 读回；`GET` 未生成过时 `data` 字段会被 NON_NULL 序列化整个省略，前端统一成 `null` 处理。
- **删除账号暂不级联删除同步数据。** `sync_job` 与各数据表对 `garmin_account` 有外键约束，需要在同一事务里先清理。

- 每完成一个功能，同步commit代码，不需要推送。
