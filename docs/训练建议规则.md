# 训练建议规则（readiness-v1）

对应实现：`server/src/main/java/com/trainingplan/platform/service/training/TrainingAdviceEngine.java`
规则版本号：`readiness-v2`（接口返回的 `ruleVersion` 字段）

本文件是「可解释」的落点：**每一条灯色都要能回答「为什么是这个颜色」**，
所以阈值、依据、以及不参与判灯的字段都写在这里。改阈值必须同时改这里和
`TrainingAdviceEngineTest`。

---

## 一、六个输入与各自角色

| 输入 | 来源 | 参与判灯 | 数据新鲜度要求 |
|---|---|---|---|
| 训练状态与负荷 | `training_status`（Garmin 测算） | ✅ | 当天或前一天 |
| HRV | `hrv_record`（Garmin 测算） | ✅ | **当天** |
| 睡眠 | `sleep_record` | ✅ | **当天** |
| 主观疲劳 RPE | `daily_checkin`（用户手填） | ✅ | **当天** |
| FTP | `ftp_history` | ❌ 仅换算瓦数 | 生效不超过 90 天 |
| 体重 | `daily_checkin`（用户手填） | ❌ 仅算 W/kg | 近 14 天 |

FTP 与体重是 `INFO` 而非恢复依据：**FTP 高不抵消恢复异常，体重变化也不作为疲劳或脱水结论**
（单次体重波动主要是水分，用它下结论会误导）。

## 二、四个恢复维度如何判色

### 2.1 训练状态与负荷（`training`）

Garmin 的 `trainingStatusFeedbackPhrase` 去掉尾部数字后比较（如 `PRODUCTIVE_6` → `PRODUCTIVE`）。

| 条件 | 灯色 |
|---|---|
| `OVERREACHING`，或 `acwrStatus = VERY_HIGH`，或 `acwrRatio ≥ 2.0` | 🔴 |
| `STRAINED` / `UNPRODUCTIVE` / `RECOVERY` / `DETRAINING`，或 `acwrStatus = HIGH`，或 `acwrRatio ≥ 1.5` | 🟡 |
| 其余可识别状态 | 🟢 |

**ACWR 比值 1.5 / 2.0 是对状态缺失的兜底，不是独立判据。** 实测 200 天里
`acwrStatus` 与 `acwrRatio` 完全一一对应，无重叠：

| `acwrStatus` | 天数 | 比值范围 |
|---|---|---|
| `LOW` | 76 | 0.00 – 0.70 |
| `OPTIMAL` | 93 | 0.80 – 1.40 |
| `HIGH` | 22 | 1.50 – 1.90 |
| `VERY_HIGH` | 9 | 2.00 – 2.80 |

所以两条判断在正常数据下等价；保留比值判断只针对「状态字段为空但比值存在」
的情况。若将来 Garmin 改了分档口径，这里会出现分歧，届时以本表重新核对为准。

**低负荷不自动要求补强度**：`acwrStatus = LOW` 不判黄灯，只记绿灯。
低 ACWR 说明近期练得少，是否需要加量取决于恢复状态与目标，
不该由一条规则替用户决定。

**空快照不当正常**：状态与 `acwrStatus` 都无法识别、且比值为空时，
判为「数据待补齐」而不是绿灯。

### 2.2 HRV（`hrv`）

需要**当天**数据。两天前的 HRV 不能替代今晨状态——这是本规则里唯一要求当天
Garmin 数据的维度。

两种情况之一成立即视为异常：
1. `hrvStatus` 属于 `LOW` / `POOR` / `UNBALANCED`；
2. 7 日均值落在个人基线 `[balancedLow, balancedUpper]` 之外；
3. 夜间值 ≤ 7 日均值 × 0.8（相对自身下降 20%）。

| 条件 | 灯色 |
|---|---|
| 当天异常，且**前两个日历日也异常**（连续 3 天） | 🔴 |
| 当天异常 | 🟡 |
| 无异常 | 🟢 |

**为什么用 7 日均值对基线，而不是当天值对基线**：单夜 HRV 噪声大，
Garmin 的个人基线本身就是按 7 日均值滚动的，用同口径比较才成立。

**必须有基线或可识别状态**，否则判「数据待补齐」：HRV 的绝对毫秒数不能跨人比较
（同一个人 70 ms 可能是异常，另一个人是正常），没有基线就没有判据。

### 2.3 睡眠（`sleep`）

取**当天最长的一次有效睡眠**：午睡不覆盖主睡眠，重复记录也不累加
（Garmin 对同一天可能返回多条，累加会得出 12 小时的假数据）。
有效指 `0 < sleepTimeSeconds ≤ 86400`。

| 条件 | 灯色 |
|---|---|
| `< 4` 小时 | 🔴 |
| `< 6` 小时，或评分 `< 60` | 🟡 |
| 其余 | 🟢 |

**6 小时与趋势看板同口径**：前端 `TrendsView.vue` 的 `SHORT_SLEEP_HOURS = 6`，
两处不能各写一套，否则同一份睡眠在趋势页是「需留意」、在建议里是「正常」。
4 小时以下视为严重剥夺，直接红灯。
评分缺失不判黄灯（只用时长），避免因为设备不给评分就长期挂黄灯。

### 2.4 主观疲劳 RPE（`rpe`）

需要**当天**填写，1–10。

| 条件 | 灯色 |
|---|---|
| `≥ 9` | 🔴 |
| `≥ 7` | 🟡 |
| `≤ 6` | 🟢 |

**不沿用昨天的 RPE**：本字段是**晨间疲劳**，不是课后用力程度。沿用会把
「昨晚练得很狠」误读成「今早很疲劳」，两者要采取的行动相反。

## 三、四色如何合成一个灯

四个恢复维度中，统计**可用**（有数据、且在新鲜期内）的条数 `n` 与黄灯数 `w`：

```
红灯 = 任一维度红灯，或 w ≥ 2
黄灯 = 有黄灯，或 n < 3
绿灯 = n ≥ 3 且无黄灯
```

- **两个黄灯升红灯**：单个维度异常可能是噪声，两个维度同时异常说明是真实的累积疲劳。
- **`n < 3` 才压到黄灯**：缺**一**项但没有任何维度异常时放行绿灯，处方按证据完整度收紧（见第四节）。
- 置信度：`n = 4` → `HIGH`，`n ≥ 2` → `MEDIUM`，否则 `LOW`（缺一项时是 `MEDIUM`）。

### ⚠️ 为什么是 3 而不是 4（readiness-v1 → v2 的改动）

`readiness-v1` 要求 `n = 4` 才给绿灯，实测**在真实使用中把绿灯变成了不可达状态**：

| | v1（要求 n=4） | v2（n≥3） |
|---|---|---|
| 绿灯 | **0 天** | **57 天** |
| 黄灯 | 139 天 | 82 天 |
| 红灯 | 61 天 | 61 天 |
| 处方分布 | 恢复骑 139 / 休息 61 | **基础有氧 45min 57** / 恢复骑 82 / 休息 61 |

（本地 200 天真实数据，2026-03-06 ~ 2026-09-21）

原因是四个恢复维度里**只有 RPE 需要人工填写**：可用依据为 `3/4` 的有 184 天，差的
全部是 RPE。于是 v1 下「不缺任何数据」几乎不可能成立。

更关键的是它与训练目标直接冲突：同期 Garmin 负荷平衡诊断为
`AEROBIC_LOW_SHORTAGE`（低强度有氧只有目标下限的 36%），而 v1 因为缺一条手填数据
把每天都锁在 20 分钟 Z1 恢复骑上——**恰恰不给最该练的 Z2**。典型例子：

> 2026-07-12：三个 Garmin 维度全绿（有效训练 · ACWR 0.90、HRV 77/85 在基线 69–92 内、
> 睡眠 7.8 小时 86 分）。v1：黄灯 + 20 分钟 Z1 恢复骑。v2：绿灯 + 45 分钟 Z2 有氧。

**v2 的取舍**：缺一项不等于数据不可信——三项无异常的客观/主观依据已经足够支撑
一次**有上限的**有氧训练。所以不是简单放行，而是「放行 + 收紧」：处方时长与强度
都随证据完整度下降，四项齐全才给到 60 分钟。

**未采纳的方向**：允许 3 天内沿用 RPE 会削弱「晨间疲劳」的口径（把「昨晚练得狠」
误读成「今早很疲劳」，两者该采取的行动相反），留待单独决定。

## 四、处方如何生成

### 4.1 规则引擎（不调用模型）

| 灯色 / 可用数 | 类型 | 内容 |
|---|---|---|
| 红灯，或 `n = 0` | `REST` | 0 分钟，不安排骑行课 |
| 黄灯 | `RECOVERY` | 20 分钟：热身 5 + 恢复骑 10 + 放松 5，全程 40–50% FTP |
| 绿灯 | `ENDURANCE` | 见下 |

绿灯的时长取决于**证据完整度**与 Garmin 的负荷平衡诊断：

| 条件 | 时长 | 主段强度 | 计划名称 |
|---|---|---|---|
| `AEROBIC_LOW_SHORTAGE` 且 `n = 4` | 60 分钟（热身 10 + 主段 45 + 放松 5） | Z2 · 60–70% FTP | 60 分钟基础有氧 |
| 其余且 `n = 4` | 45 分钟（热身 10 + 主段 30 + 放松 5） | Z2 · 60–70% FTP | 45 分钟稳定有氧 |
| `n = 3`（缺一项） | 45 分钟（热身 10 + 主段 30 + 放松 5） | Z2 · 60–70% FTP | 45 分钟有氧（恢复依据不全，已收紧） |

**缺一项时收到 45 分钟，但绝不退回恢复骑**：低强度有氧不足时最该练的就是 Z2，
为了保守而改回 Z1 是本末倒置。代价体现在时长上限，而不是取消训练。

**绿灯不自动追加间歇课**：恢复指标正常不等于该上强度，强度安排属于周期化决策。
低强度有氧不足时优先补 Z2 的**量**，而不是加 Z4/Z5 的强度。

**瓦数由服务端按有效 FTP 换算**（`round(ftp × 百分比 / 100)`），
模型只输出百分比。没有有效 FTP 时只给百分比与体感指引。
W/kg = `round(FTP ÷ 体重 × 100) / 100`，缺体重则不计算（不猜、不显示 0）。

### 4.2 模型生成（显式点击才调用）

`TrainingPlanServiceImpl` 调 DeepSeek 生成**当天**处方，并做结构与安全校验：

- `steps` 最多 8 段；每段分钟为正整数且 `≤` 上下文给出的时长上限；
- FTP 百分比为正整数，下限 `≤` 上限，且 `≤` 上下文给出的强度上限；
- 总时长不得超过上限；`maxDurationMinutes = 0` 时必须 `steps = []`；
- 上限随证据完整度收紧：红灯 0 分钟/0%，黄灯 20 分钟/50%，绿灯 `n = 4` 90 分钟/75%、`n = 3` 45 分钟/70%（与规则引擎的处方一致，模型只能在窗口内安排）；
- 校验失败抛 `AI_INVALID_RESPONSE`，**不记录模型原文**（避免把私人健康数据写进日志）。

**模型只能改「怎么练」，不能改「能不能练」**：灯色由规则引擎算出，
模型不得修改既有恢复判灯；数据不足时模型被要求保守安排并说明何时重新评估。

提示词明确把用户数据（包括 `note`）标为分析材料、不得执行其中的指令，
并要求不编造缺失数据、不做医学诊断或减重目标。

## 五、变更约定

- 改任何阈值：同步更新本文件 + `TrainingAdviceEngineTest`，并提升 `RULE_VERSION`。
- 新增恢复维度：必须同时考虑「缺失时是否压灯」，否则会出现维度越多、绿灯越难的情形。
- 本文件中的实测数字来自本地 200 天真实数据（2026-03-06 ~ 2026-09-21），
  数据变化后应重新核对。
- **降低放行门槛时必须同时收紧处方**。`readiness-v1 → v2` 把绿灯门槛从 4 项降到 3 项，
  同时把缺证据时的时长从「不给训练」改成「给 45 分钟且标注已收紧」。只降门槛不收紧
  上限，等于单方面放松安全规则。
- **缺一项的手填数据不该锁死整个处方**。新增或调整恢复维度时，先确认它需要人工输入
  的比例：如果某个维度必须每天手填，而它缺失就压灯，绿灯会长期不可达（v1 的实测
  后果就是绿灯 0 天）。
