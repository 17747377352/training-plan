所有数字为 **2026-09-24** 在真实账号（Garmin 国际站，账号信息不写入仓库）连续 13 天
（2026-09-12 ~ 2026-09-24，含 3 次骑行、3 次午睡）的真实 SQLite 与真实平台库上实测。

上游：`garmin-givemydata==0.1.13`（PyPI 安装版，非仓库快照）。
映射实现：`scripts/mapping.py`。

## 二、逐类明细

### 1. DailyHealthDto —— 11/11 ✅

源表 `daily_summary`，按 `calendar_date` 取。

`calendarDate` ← `calendar_date`；其余 10 项：`steps` ← `total_steps`、`distanceMeters` ←
`total_distance_meters`、`totalKilocalories` ← `total_kilocalories`、`activeKilocalories` ←
`active_kilocalories`、`restingHeartRate` ← `resting_heart_rate`、`minHeartRate` ← `min_heart_rate`、
`maxHeartRate` ← `max_heart_rate`、`averageStressLevel` ← `average_stress_level`、
`bodyBatteryHighest` ← `body_battery_highest`、`bodyBatteryLowest` ← `body_battery_lowest`。

### 2. SleepRecordDto —— 12/12 ✅

源表 `sleep`，但要钻到 `raw_json` 里取时间：

- `sleepStartGmt` ← `raw.dailySleepDTO.sleepStartTimestampGMT`（**epoch 毫秒**，不是 `sleep` 表顶层列）
- `sleepEndGmt` ← `raw.dailySleepDTO.sleepEndTimestampGMT`
- `avgSleepHrv` ← `raw.avgOvernightHrv`
- 其余 8 项来自表列：`sleepTimeSeconds` ← `sleep_time_seconds`、`deepSleepSeconds` ←
  `deep_sleep_seconds`、`lightSleepSeconds` ← `light_sleep_seconds`、`remSleepSeconds` ←
  `rem_sleep_seconds`、`awakeSleepSeconds` ← `awake_sleep_seconds`、`sleepScore` ←
  `sleep_score_overall`、`avgSpo2` ← `average_spo2`、`avgRespiration` ← `average_respiration`

`average_spo2` 实测 12/13，缺的那天设备未记录 → 允许为空。

### 3. NapRecordDto —— 6/6 ✅

源：`raw.dailySleepDTO.dailyNapDTOS` 数组，**只有当天真的午睡过才出现该键**。
曾经因为「抽样的那天没有午睡」而误判成上游不提供 —— 判断某字段是否存在，不能只看一天的样本。

`calendarDate` ← `nap.calendarDate`（缺则退回 `sleep.calendar_date`）、`napStartGmt` ←
`napStartTimestampGMT`、`napEndGmt` ← `napEndTimestampGMT`、`napSeconds` ← `napTimeSec`、
`napFeedback` ← `napFeedback`、`napSource` ← `napSource`。

缺开始时间的午睡会直接报错，不做静默丢弃。

### 4. HrvRecordDto —— 7/7 ✅

源表 `hrv`：`lastNightAvg` ← `last_night_avg`、`weeklyAvg` ← `weekly_avg`、`status` ← `status`、
`baselineLowUpper` ← `baseline_low`、`baselineBalancedUpper` ← `baseline_upper`、
`baselineBalancedLow` ← **`raw.baseline.balancedLow`**（在原始响应里，不是表列 —— 漏掉会整列为空）。

实测 `balancedLow` 有值（如 75 / 81 / 106）。

### 5. ActivityDto —— 37/49 ⚠️

源表 `activity`，按 `start_time_local` 取，且**只保留骑行**
（`activity_type` 含 `cycling`/`biking`，或 `parent_type_id = 2`）。

已填（含实测非空）：

- 3 项由映射显式写入：`activityName` 固定为「骑行」（**不带上游的活动名，避免位置信息**）、
  `startTimeGmt`、`startTimeLocal`
- `garminActivityId`、`activityTypeKey`、`activityTypeId`、`parentTypeId`
- 时长与距离：`durationSeconds`、`movingDurationSeconds`、`elapsedDurationSeconds`、`distanceMeters`
- 爬升：`elevationGain`、`elevationLoss`、`maxElevation`、`minElevation`
- 速度与心率：`averageSpeed`、`maxSpeed`、`averageHr`、`maxHr`
- 热量：`calories`、`bmrCalories`
- 功率与负荷：`avgPower`、`maxPower`、`normPower`、`intensityFactor`、`trainingStressScore`
- 踏频与训练效果：`avgCadence`、`maxCadence`、`aerobicTrainingEffect`、`anaerobicTrainingEffect`、
  `activityTrainingLoad`
- 其它：`lapCount`、`avgRespirationRate`、`minTemperature`、`maxTemperature`、`vo2maxValue`、`deviceId`

无源（不要试图去修）：

- 功率区间 `powerZone1Seconds`、`powerZone2Seconds`、`powerZone3Seconds`、`powerZone4Seconds`、
  `powerZone5Seconds`、`powerZone6Seconds`、`powerZone7Seconds`：只在**活动详情**响应里，上游 0.1.13
  不把详情写库（`activity` 表只有汇总行）。映射里已留前向兼容代码，上游一旦持久化详情就自动生效。
- `avgElevation`、`max20minPower`、`avgLeftBalance`、`trainingEffectLabel`、`strokes`（共 5 项）：
  上游 `activity` 表**没有这些列**（`PRAGMA table_info(activity)` 已核对）。

### 6. TrainingStatusDto —— 12/22 ⚠️

源表 `training_status`，ACWR 与负荷隧道藏在**两层嵌套**里：
`raw.mostRecentTrainingStatus.latestTrainingStatusData[<设备ID>].acuteTrainingLoadDTO`
（取 `primaryTrainingDevice = true` 的那台设备，否则取第一台）。只挖一层会整片丢失，
且**不会报错**，只会让判灯变保守。

- 来自 `acuteTrainingLoadDTO`：`acwrPercent`、`acwrStatus`、`acwrRatio` ←
  `dailyAcuteChronicWorkloadRatio`、`acuteLoad` ← `dailyTrainingLoadAcute`、`chronicLoad` ←
  `dailyTrainingLoadChronic`、`chronicLoadMin` ← `minTrainingLoadChronic`、`chronicLoadMax` ←
  `maxTrainingLoadChronic`
- 来自条目本身：`trainingStatus`、`trainingStatusPhrase` ← `trainingStatusFeedbackPhrase`
  （缺失时退回上游 `status` 列，避免整列为空）
- 来自旁表（按日期对齐）：`vo2maxValue` ← `vo2max` 表**取 `sport = 'CYCLING'`**
  （同一天也有 `RUNNING`，取错会让阈值静默偏高一档）、`fitnessAge` ← `fitness_age.fitness_age`

无源（**真无源，不是接线活**）：

- 以下 10 项无源：`loadAerobicLow`、`loadAerobicLowTargetMin`、`loadAerobicLowTargetMax`、
  `loadAerobicHigh`、`loadAerobicHighTargetMin`、`loadAerobicHighTargetMax`、`loadAnaerobic`、
  `loadAnaerobicTargetMin`、`loadAnaerobicTargetMax`、`balanceFeedbackPhrase`。
  上游 `load_focus` 表有建表语句，但**没有任何端点、也没有 upsert**，所以浏览器路径永远拿不到。

  **但要分清「浏览器路径拿不到」和「平台没有」**：平台库里这些字段是**有值**的 ——
  开发库 214 行训练状态里有 **201 行填满了**这一族（`load_aerobic_low` 及其 target、
  `load_aerobic_high` 一族、`load_anaerobic` 一族、`balanceFeedbackPhrase` 各 201 行非空），
  因为**令牌路径**（`python-garminconnect` 的训练状态接口）本来就能给。所以这是
  「换成本机浏览器上传后，某个账号这一族会缺」的问题，而不是平台能力缺失。

  **混用不会互相抹掉**（已实测）：平台 upsert 用的是 MyBatis-Plus `updateById`，默认策略
  **忽略 null 字段**。在账号 20 上把 `load_aerobic_low=36 / load_anaerobic=99 /
  balanceFeedbackPhrase='PROBE'` 当作「令牌路径留下的值」写入，再用浏览器路径重传同一天，
  三个值**原样保留**，而浏览器能提供的字段（`acwr_percent`、`fitness_age`、`vo2max_value`）
  正常更新。也就是说：同一账号先用令牌路径补齐负荷分布、之后转浏览器上传，
  **已经采到的负荷分布不会被清空**（探针值已清理还原）。
- `training_readiness`、`endurance_score`、`hill_score` 三张表同理为空，但原因不同：
  上游**确实请求了**这些端点（`training_readiness` 在 `full_range_graphql`，
  `endurance_score`/`hill_score` 在 `daily_rest`），是本账号返回空 —— 原始响应对照为
  `endurance_score` / `hill_score` 全为 `{"data": null, "status": 204}`，
  `training_readiness` 为 `{"trainingReadinessRangeScalar": []}`。
  即：**账号/设备侧没有这些指标**，补调用也拿不到；且平台侧目前没有对应字段。

### 7. FtpHistoryDto —— 无接口，但**已按 IF 定义反解**（2/2 ✅）

上游 0.1.13 没有 FTP 历史接口，因此 `effectiveDate` 与 `ftpWatts` 都填不出来；
`lactate_threshold` 只存**阈值心率**与速度，**没有功率**，不能冒充 FTP。
`upload` 会在 `warnings` 里明确报告这一点，不静默留空。

**但是**：FTP 不必从新接口拿 —— Garmin 的 IF 定义就是 `IF = NP / FTP`，所以
`FTP ≈ norm_power / intensity_factor`，而这两个字段**已经在活动汇总里、也已经入库**。
实测三次骑行（2026-09-12 / 16 / 19）：

| 日期 | NP | IF | NP/IF 反推 FTP | 由 TSS 公式独立反推 |
|---|---|---|---|---|
| 2026-09-12 | 179 | 0.838 | **213.6** | 217.5 |
| 2026-09-16 | 161 | 0.756 | **213.0** | 213.2 |
| 2026-09-19 | 186 | 0.874 | **212.8** | 214.8 |

三次独立反推只差 0.8 W（0.4%），两条公式互相印证，说明这个值稳定可用。

**而且它与真值对得上**：同账号此前用**令牌路径**（`get_cycling_ftp`，本机浏览器上传拿不到这个接口）
同步过 18 条真实 FTP 历史，最近一条 `2026-08-29 = 213 W`；上述 9 月三次骑行的反推值为
213.0 ~ 213.6 W，**与真值相差不到 1 W**。也就是说：浏览器路径虽然拿不到 FTP 接口，
却能把「当前 FTP」反推得相当准（依据是本账号两条独立数据路径的交叉验证，不是理论推测）。

**已按此实现**（2026-09-24 决定采用）：映射取 `round(norm_power / intensity_factor)`，
同一天多次骑行只留时长最长的那次，落库时带 `source=DERIVED`；平台侧 `FtpHistoryDto` 增加
`source` 字段，`upsertFtpHistory` 只接受白名单 `GARMIN / DERIVED / MANUAL`（空值按 `GARMIN`，
兼容只报两个字段的采集器），未知值整批拒绝而不是静默改标。实测账号 20（浏览器路径）
落库为 214 / 213 / 213 W 且 `source=DERIVED`，同库令牌路径的 18 条仍是 `GARMIN`，两者没有混淆。

采用时明确的几点：

- 它反推的是**设备里当前设置的 FTP**，不是实测值，也没有历史：换了 FTP 之后旧活动仍指向旧值，
  所以只能给「当前值」，不能当真恢复出历史曲线。
- 精度受 Garmin 对 IF 的取整限制（约 ±1 W），且**只有带功率计、有 NP 与 IF 的骑行**才有。
- 字段名是「FTP 历史」，而这是派生值，所以必须带来源标记 `DERIVED`，不能让它看起来像
  Garmin 报出来的 FTP —— 这正是原先「不能把功率冒充 FTP」那条约束的边界：
  `avg_power` 冒充 FTP 是错的，而按 Garmin 自己的 IF 定义反解是另一回事，但**仍属派生**。
- 反解结果只在 `[80, 700]` W 之内才采信；缺 `norm_power`/`intensity_factor`、IF ≤ 0 或越界
  一律跳过（宁可不给，也不要上报一个会把处方强度带偏的数）。

### 8. ActivityHrZoneDto —— 3/3 ✅

源表 `activity_hr_zones`，`raw_json` 是数组（也可能包在 `heartRateZones` 下）：
`zoneNumber` ← `zoneNumber`、`zoneLowBoundary` ← `zoneLowBoundary`、`secondsInZone` ←
`secsInZone`（**小数秒要取整**）。

只上传本次活动列表里出现过的活动 ID，避免历史区间混进本批。

## 三、对判灯与处方的影响

- **可用**：每日健康、睡眠时长与分期、午睡、HRV 与基线、骑行功率/心率/TSS/踏频/训练效果、
  ACWR 三件套与负荷隧道、心率区间分布、VO2max、体能年龄、设备 ID。
- **缺 FTP** → 处方强度只能用 HR 区间或 RPE 表达，不能用 %FTP。
- **缺负荷分布（有氧低/高、无氧）** → 「低强度有氧不足」这类诊断没有数据支撑，
  判灯应回退到心率区间与 TSS 的组合判断，不要伪造结论。
- **缺功率区间** → 间歇质量只能看平均/标准化功率与 TSS，无法看区间命中分布。
